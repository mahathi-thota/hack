You are an expert full-stack + on-device AI engineer building a hackathon MVP for problem statement PS-I2: "Intelligence Without the Data Centre."

GOAL
Build a working, demo-ready MVP of an offline-first mobile/web app that lets a citizen scan or open a government form and ask natural-language questions about it — including at least one question that requires REASONING over an eligibility rule, not just field lookup — with the answer entirely generated on-device (no network calls at inference time). Initial language support: English (en) and Telugu (te), architected so the other five languages (hi, bn, ta, mr, kn) can be added by just dropping in more data/prompt templates.

CONTEXT / DATASET (The dataset (psi2.csv) will be uploaded separately into the project's /data folder.
Load it automatically at runtime.)
- CSV columns: qid, form_id, form_type, lang, type, question, answer
- form_type ∈ {scholarship, ration_card, old_age_pension}
- type ∈ {extraction, reasoning} — "extraction" = copy a field value (e.g. applicant name, district, annual income, family members, category); "reasoning" = apply a rule (e.g. "Based on the income cap and household size rule, is this applicant eligible? Answer yes or no.")
- Same qid pattern across 7 languages (en, hi, bn, te, ta, mr, kn) for the SAME underlying form — the corpus is parallel by construction, so any per-language accuracy gap is a property of the model/tokenizer, not the question.
- ~120 forms, 5,040 QA pairs total.

CORE REQUIREMENTS FROM THE PROBLEM STATEMENT (must all be visibly represented in the MVP, even if some are stubbed/simulated given the 3–4 hour build window)
1. App must conceptually run in aeroplane mode — no inference-time network calls. Simulate on-device LLM inference via a local/offline-capable module (e.g., a mocked llama.cpp/Qwen/Gemma-style inference wrapper with a clearly marked TODO/plug-in point for the real quantized GGUF model).
2. Pipeline: form image or text → OCR (stub with Tesseract.js or a placeholder OCR module) → retrieval over the form's own fields (simple keyword/embedding retrieval over structured field data) → local LLM answers the question → return answer + which field it came from (source attribution).
3. Must handle both extraction questions (direct field lookup) and reasoning questions (apply an eligibility rule like income cap + household size) — clearly differentiate these two question types in the UI and in the retrieval/answer logic.
4. Accuracy reporting must be PER LANGUAGE and PER QUESTION TYPE (extraction vs reasoning) separately — never a single blended aggregate number. This is the central "trap" the problem statement warns about: aggregate numbers hide catastrophic drops in low-resource languages.
5. Include a "Measurements / Analytics" dashboard page showing (using placeholder/simulated data clearly labeled as such, with a TODO to wire up real device telemetry): cold-start model load time, prefill/decode tokens-per-second, peak RSS memory, sustained throughput after thermal soak, and a tokenizer fertility table across languages (before/after tokenizer intervention). Present these as distributions (histograms/box plots), not single best-case numbers.
6. Must show a "Limits" section (what's simulated vs real, target device class ≤₹12,000, target resident memory ≤1.2GB) to be transparent with judges.
